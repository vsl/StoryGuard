# BM25 Retrieval Baseline

## Hypothesis

Elasticsearch's default BM25 similarity should provide a useful first lexical
retrieval baseline for exact names and terms. It should be weaker when a query
and relevant passage express the same concept with different words.

## Developer prediction

The developer predicted that exact overlap such as `Alex` would work well, while
a query for `car` could miss a passage that mentions only `BMW`. BM25 is needed
both as a measurable baseline for embeddings and as the lexical branch of later
hybrid retrieval.

## Baseline

- Elasticsearch: `8.19.19`;
- similarity: default BM25;
- query: `match` over `text`;
- mandatory filters: `project_id` and `manuscript_version_id`;
- requested candidate K: `30`;
- physical index: `storyguard-chunks-v1`.

This is the first retrieval baseline, so there is no earlier retriever candidate
to compare or replace. Vector retrieval becomes the first meaningful candidate
in lesson 3.2.

## Dataset and version

- registry source: pinned `illuin-conteb/narrative-qa` revision
  `93e4c746bc03c3a9def375302b4d570c21abbd34`;
- transform: `storyguard-datasets-v1`;
- queries: `20`;
- indexed candidate documents: `3`.

The local fixture is a smoke benchmark, not a representative retrieval corpus.
In particular, Recall@5 and larger K cannot discriminate strategies when only
three documents exist.

## Metrics

| Metric | BM25 |
|---|---:|
| Recall@1 | 0.80 |
| Recall@5 | 1.00 |
| Recall@10 | 1.00 |
| Recall@30 | 1.00 |
| MRR | 0.875 |
| Median retrieval latency | 10.10 ms |

There were 16 rank-1 queries, one rank-2 query, and three rank-3 queries. No LLM,
embedding model, paid API, or LangSmith trace was involved, so model cost was
zero and there are no trace or experiment IDs.

## Failure analysis

The query asking what led to dismantling Mark's station and his arrest labels
chunk `_2` as the sole relevant document. Chunk `_2` contains the preceding FCC
investigation, while chunk `_3` directly describes dismantling the station,
creating the mobile transmitter, the pursuit, and the arrest. BM25 ranked `_3`
ahead of the labeled `_2` and was therefore penalized for returning the more
direct evidence.

The developer correctly identified this as a ground-truth labeling failure. More
precisely, it is incomplete relevance labeling for a multi-part query: `_2` is
useful precursor evidence and `_3` answers the main requested event. The current
single `relevant_chunk_id` schema cannot express both.

The qualitative `car` versus `BMW` semantic-failure prediction was not tested by
this fixture and remains a hypothesis for the vector comparison.

## Security and reliability checks

- a Project A query returned no Project B chunks;
- a current-version query returned no old-version chunks;
- repeated version indexing replaced documents instead of duplicating them;
- partial bulk failures were rejected;
- the complete backend suite passed `19/19` tests with live PostgreSQL, MinIO,
  RabbitMQ, and Elasticsearch dependencies.

## Developer conclusion and discussion

The developer concluded that chunk `_3` is the direct answer and the observed
rank penalty comes from faulty ground truth rather than a demonstrated BM25
failure. The discussion refined this to incomplete multi-evidence labeling:
chunk `_2` contains relevant causal setup, but `_3` is indispensable.

## Decision

Keep BM25 as the provisional lexical baseline. Do not tune BM25 against these
noisy labels and do not silently rewrite the pinned fixture. Before using this
dataset for a serious BM25/vector promotion decision, expand the corpus and let
the evaluation schema represent multiple relevant chunks.
